# Help Desk Ticket System — PostgreSQL Schema v1

This document explains the PostgreSQL schema represented by `docs/database-schema.sql`.

The SQL file is the reference schema for the initial database design. The actual application database will later be created and evolved through Flyway migrations.

## 1. Tables

The MVP contains exactly five core tables:

1. `users`
2. `categories`
3. `tickets`
4. `comments`
5. `ticket_audits`

There is deliberately no separate `agents` table.

A support agent is a row in `users` with:

```text
role = SUPPORT_AGENT
```

## 2. Identifier strategy

Internal entities use UUID primary keys:

* `users.id`
* `categories.id`
* `tickets.id`
* `comments.id`
* `ticket_audits.id`

Tickets additionally have a human-facing sequential number:

```text
ticket_number BIGINT GENERATED ALWAYS AS IDENTITY
```

This produces numbers such as:

```text
1
2
3
...
```

The UUID remains the internal entity identifier.

## 3. Controlled values

The schema uses `VARCHAR` plus `CHECK` constraints rather than PostgreSQL enum types for application-controlled values.

This keeps future application changes and migrations more flexible while still preventing invalid database values.

### User roles

```text
USER
SUPPORT_AGENT
ADMIN
```

### Ticket statuses

```text
OPEN
IN_PROGRESS
RESOLVED
CLOSED
```

### Ticket priorities

```text
LOW
MEDIUM
HIGH
URGENT
```

## 4. Referential integrity

### Ticket → Category

`tickets.category_id` references `categories.id`.

Deletion is restricted.

Categories should normally be deactivated rather than deleted so historical tickets retain a valid category reference.

### Ticket → Requester

`tickets.requester_id` references `users.id`.

Deletion is restricted to preserve ticket history.

### Ticket → Assigned Agent

`tickets.assigned_agent_id` references `users.id` and is nullable.

The foreign key guarantees that the referenced user exists.

The service layer additionally guarantees that an assigned user:

* is active;
* has role `SUPPORT_AGENT`.

### Ticket → Resolution confirmer

`tickets.resolution_confirmed_by` references `users.id` and is nullable.

The service layer guarantees that the confirmer is the ticket requester.

### Comment → Ticket/User

`comments.ticket_id` references `tickets.id`.

`comments.author_id` references `users.id`.

Comments are cascade-deleted with a ticket.

Users are not physically deleted through the application.

### Audit → Ticket/User

`ticket_audits.ticket_id` references `tickets.id`.

`ticket_audits.actor_id` references `users.id` and is nullable so future system-generated events can be represented without requiring a human user.

## 5. Resolution confirmation fields

The ticket stores:

* `resolution_confirmed_at`
* `resolution_confirmed_by`

Both values must either be null together or be populated together.

When populated, the ticket status must be:

```text
RESOLVED
```

or:

```text
CLOSED
```

When a requester rejects a resolution:

1. confirmation timestamp is cleared;
2. confirmation user is cleared;
3. status becomes `OPEN`;
4. the same assigned agent is retained.

The service layer is responsible for enforcing the requester and workflow rules.

## 6. Audit details

`ticket_audits.details` uses PostgreSQL `JSONB`.

This allows different event types to store structured information without requiring a large collection of nullable columns.

Example status-change details:

```json
{
  "oldStatus": "OPEN",
  "newStatus": "IN_PROGRESS"
}
```

Example assignment details:

```json
{
  "previousAgentId": null,
  "newAgentId": "uuid"
}
```

Example priority-change details:

```json
{
  "oldPriority": "MEDIUM",
  "newPriority": "URGENT"
}
```

The backend creates audit records transactionally with the business operation.

## 7. Timestamp strategy

All timestamps use:

```text
TIMESTAMPTZ
```

`created_at` is generated by PostgreSQL.

`updated_at` is maintained by a shared database trigger for tables that contain mutable records.

Reopening a ticket updates the ticket row, which refreshes `updated_at`.

Therefore reopened tickets naturally move to the top of the default:

```text
updated_at DESC
```

ordering.

## 8. Index strategy

The initial indexes target expected access patterns:

* users by `(role, active)`;
* tickets by requester and updated time;
* tickets by assigned agent and updated time;
* tickets by status and updated time;
* tickets by priority and updated time;
* tickets by category and updated time;
* comments by ticket and creation time;
* audits by ticket and creation time;
* audits by actor and creation time;
* audits by action and creation time.

Additional indexes should only be introduced when actual query patterns justify them.

## 9. Important service-layer rules

The database intentionally does not attempt to encode every application business rule.

Spring Boot services/security enforce:

* only admins assign, reassign, or unassign;
* assigned users must be active support agents;
* only the requester can edit an `OPEN` ticket;
* only assigned agents can start and resolve their tickets;
* only the requester can confirm or reject resolution;
* only admins can close tickets;
* an admin can close only a confirmed resolved ticket;
* rejection reopens a ticket while retaining the same assigned agent;
* a closed ticket cannot be reopened;
* deactivated users cannot authenticate;
* users cannot self-select elevated roles during registration;
* new ticket requester identity comes from the authenticated user;
* comment author identity comes from the authenticated user;
* audit records are generated by the backend.

## 10. Initial seed categories

The initial SQL seeds the six categories represented by the current frontend:

* `GENERAL`
* `TECHNICAL`
* `BILLING`
* `ACCOUNT`
* `BUG_REPORT`
* `FEATURE_REQUEST`

These are seed data rather than database enum values.

Administrators can later create additional categories.

Categories are deactivated rather than physically deleted when they are no longer intended for new tickets.
