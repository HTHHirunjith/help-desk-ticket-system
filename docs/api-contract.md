# Help Desk Ticket System — API Contract v1

**Status:** Implementation baseline / source of truth
**API version:** `v1`
**Base path:** `/api/v1`
**Authentication:** JWT Bearer tokens

## 1. Purpose

This document defines the HTTP API contract for the Help Desk Ticket System.

Backend and frontend implementations must conform to this contract. AI coding agents must not change endpoint semantics, request/response ownership, authorization rules, or business-state transitions silently.

If an implementation requires a contract change, update this document before changing the implementation.

## 2. Core Domain Rules

### 2.1 Roles

* `USER` — creates and follows their own support tickets.
* `SUPPORT_AGENT` — investigates and resolves tickets assigned to them.
* `ADMIN` — manages users, categories, assignments, tickets, and final closure.

A user's role is controlled by the server. Self-registration always creates `USER`.

### 2.2 Ticket statuses

* `OPEN`
* `IN_PROGRESS`
* `RESOLVED`
* `CLOSED`

Normal lifecycle:

```text
OPEN -> IN_PROGRESS -> RESOLVED -> CLOSED
```

Resolution workflow:

```text
RESOLVED
   |-- requester confirms --> confirmed RESOLVED -- admin closes --> CLOSED
   |
   `-- requester rejects --> OPEN -- same agent remains assigned
```

`CLOSED` is final in MVP. There is no `CLOSED -> OPEN` transition.

### 2.3 Priorities

* `LOW`
* `MEDIUM`
* `HIGH`
* `URGENT`

A requester supplies the initial priority when creating a ticket.

An assigned support agent can change the priority of their assigned tickets.

An admin can change the priority of any ticket.

### 2.4 Ticket ownership and visibility

* `USER`: only their own tickets.
* `SUPPORT_AGENT`: only tickets assigned to that agent.
* `ADMIN`: all tickets.

Authorization is always enforced by the backend. Frontend route protection is not a security boundary.

### 2.5 Assignment

Only an `ADMIN` can assign, reassign, or unassign a ticket.

`assignedAgent` may be null.

When an agent is assigned, the referenced user must:

1. exist;
2. be active;
3. have role `SUPPORT_AGENT`.

### 2.6 Ticket editing

A requester may update their own ticket's:

* title;
* description;
* category;

only while the ticket is `OPEN`.

The requester cannot use the requester-edit endpoint to modify:

* requester;
* status;
* priority;
* assignment;
* ticket number;
* timestamps;
* audit information.

### 2.7 Resolution confirmation

When an assigned agent marks a ticket `RESOLVED`, the requester can:

* confirm the resolution; or
* reject the resolution.

Confirmation keeps the ticket in `RESOLVED` and records:

* confirming requester;
* confirmation timestamp.

Rejection changes:

```text
RESOLVED -> OPEN
```

and:

* keeps the same assigned agent;
* clears resolution confirmation fields;
* refreshes `updatedAt`;
* creates a `TICKET_REOPENED` audit event.

A ticket cannot be closed until the requester has confirmed the resolution.

### 2.8 Comments

* `USER`: comments on their own tickets.
* `SUPPORT_AGENT`: comments on tickets assigned to them.
* `ADMIN`: comments on any ticket.

The comment author is always derived from the authenticated user. The client cannot choose an author ID.

### 2.9 Categories

Categories are administrator-managed data.

Admins can:

* create categories;
* update categories;
* activate categories;
* deactivate categories.

Categories are not physically deleted in the MVP.

Inactive categories cannot be selected when creating a new ticket.

A category associated with an existing ticket remains valid for historical data even if that category is later deactivated.

### 2.10 Ticket ordering and reopened tickets

Ticket lists default to:

```text
updatedAt DESC
```

Reopening a ticket updates `updatedAt`, causing it to move to the top of normal ticket lists.

The frontend should visibly identify reopened or needs-attention tickets where appropriate.

### 2.11 Audit

Important ticket events are recorded in `ticket_audits`.

Audit records are generated by the backend as part of the corresponding business operation.

Clients cannot submit or modify trusted audit data.

### 2.12 Agent availability

Agent availability such as:

```text
AVAILABLE
BUSY
OFFLINE
```

is intentionally outside MVP scope.

### 2.13 Ticket identifiers

Internal entity identifiers use UUIDs.

The human-facing ticket number is a sequential number:

```text
1, 2, 3, ...
```

The number is generated by the backend.

## 3. Authentication

Protected requests use:

```http
Authorization: Bearer <JWT>
```

The backend derives the authenticated user and role from the JWT/security context.

### 3.1 Register

```http
POST /api/v1/auth/register
```

**Access:** Public

Request:

```json
{
  "firstName": "John",
  "lastName": "Doe",
  "email": "john@example.com",
  "password": "SecurePassword123"
}
```

The request must not contain a role.

The server always creates the account with role `USER`.

Success:

```http
201 Created
```

Response:

```json
{
  "message": "Registration successful",
  "user": {
    "id": "uuid",
    "email": "john@example.com",
    "firstName": "John",
    "lastName": "Doe",
    "role": "USER",
    "active": true,
    "avatarUrl": null,
    "createdAt": "2026-09-03T10:00:00Z"
  }
}
```

Errors:

* `400 Bad Request` — validation failure.
* `409 Conflict` — email already exists.

### 3.2 Login

```http
POST /api/v1/auth/login
```

**Access:** Public

Request:

```json
{
  "email": "john@example.com",
  "password": "SecurePassword123"
}
```

Success:

```http
200 OK
```

Response:

```json
{
  "token": "<JWT>",

    "id": "uuid",

    "lastName": "Doe",
    "role": "USER",
    "active": true,
    "avatarUrl": null
  }
}
```

Errors:

* `401 Unauthorized` — invalid credentials or deactivated account.

### 3.5 User management (Admin only)

```http

```
**Access:** ADMIN only

#### Get User by ID
```http
GET /api/v1/users/{userId}
```
**Access:** ADMIN only

#### Create Privileged Account (SUPPORT_AGENT / ADMIN)
```http

```
**Access:** ADMIN only

Request:
```json
{
  "firstName": "Jane",
  "lastName": "Doe",
  "email": "jane.doe@example.com",
  "role": "SUPPORT_AGENT"
}
```

```http

```

#### Update User Profile
```http
PATCH /api/v1/users/{userId}
```
**Access:** ADMIN only
Updates permitted non-security profile fields (`firstName`, `lastName`, `email`). Role and active status cannot be modified via PATCH.

#### Activate User
```http
POST /api/v1/users/{userId}/activate
```
**Access:** ADMIN only

#### Deactivate User
```http
POST /api/v1/users/{userId}/deactivate
```
**Access:** ADMIN only
*Admin safety rules: Admin cannot deactivate themselves (400 Bad Request). Cannot deactivate the last active ADMIN (409 Conflict).*

### 4.4 Update an OPEN ticket

```http
PATCH /api/v1/tickets/{ticketId}
```

**Access:** `USER`, own ticket, status must be `OPEN`.

Request:

```json
{
  "title": "Updated title",
  "description": "Updated description",
  "categoryId": "uuid"
}
```

All supplied fields must be requester-editable fields.

The server must ignore/reject attempts to modify:

* requester;
* status;
* priority;
* assignment;
* ticket number;
* timestamps;
* audit information.

The replacement category must exist and be active.

Success:

```http
200 OK
```

Appropriate audit records are created for meaningful changes, including `CATEGORY_CHANGED` when the category changes.

Errors:

* `400 Bad Request`
* `403 Forbidden`
* `404 Not Found`
* `409 Conflict` — ticket is no longer editable because its state has changed.

### 4.5 Change priority

```http
PATCH /api/v1/tickets/{ticketId}/priority
```

**Access:**

* `SUPPORT_AGENT` → assigned ticket only.
* `ADMIN` → any ticket.

Request:

```json
{
  "priority": "URGENT"
}
```

Success:

```http
200 OK
```

If the value actually changes, create a `PRIORITY_CHANGED` audit event containing the previous and new priority.

### 4.6 Assign ticket

```http
PUT /api/v1/tickets/{ticketId}/assignment
```

**Access:** `ADMIN`

Request:

```json
{
  "agentId": "uuid"
}
```

Requirements:

* target user exists;
* target user is active;
* target user has role `SUPPORT_AGENT`.

If currently unassigned, create `TICKET_ASSIGNED`.

If changing agents, create `TICKET_REASSIGNED`.

Success:

```http
200 OK
```

### 4.7 Unassign ticket

```http
DELETE /api/v1/tickets/{ticketId}/assignment
```

**Access:** `ADMIN`

Result:

```text
assignedAgent = null
```

Create a `TICKET_UNASSIGNED` audit event.

Success:

```http
204 No Content
```

## 5. Ticket workflow actions

Workflow operations are represented by action endpoints instead of a generic status PATCH because each transition has different authorization and validation rules.

### 5.1 Start work

```http
POST /api/v1/tickets/{ticketId}/start
```

**Access:** assigned `SUPPORT_AGENT`

Transition:

```text
OPEN -> IN_PROGRESS
```

Success:

```http
200 OK
```

Creates `STATUS_CHANGED` audit data containing the old and new status.

### 5.2 Resolve

```http
POST /api/v1/tickets/{ticketId}/resolve
```

**Access:** assigned `SUPPORT_AGENT`

Allowed transition:

```text
IN_PROGRESS -> RESOLVED
```

On resolve:

* status becomes `RESOLVED`;
* resolution-confirmation fields are cleared;
* requester notification may be triggered by the notification layer when available;
* audit event records the transition.

Success:

```http
200 OK
```

### 5.3 Confirm resolution

```http
POST /api/v1/tickets/{ticketId}/confirm-resolution
```

**Access:** requester only.

Preconditions:

* status = `RESOLVED`;
* authenticated user is the requester;
* resolution has not already been confirmed.

Result:

* status remains `RESOLVED`;
* `resolutionConfirmedAt` is set;
* `resolutionConfirmedBy` is the authenticated requester;
* audit event `RESOLUTION_CONFIRMED` is created.

Success:

```http
200 OK
```

### 5.4 Reject resolution / reopen

```http
POST /api/v1/tickets/{ticketId}/reject-resolution
```

**Access:** requester only.

Precondition:

* status = `RESOLVED`.

Result:

```text
RESOLVED -> OPEN
```

and:

* same assigned agent remains assigned;
* `resolutionConfirmedAt` becomes `null`;
* `resolutionConfirmedBy` becomes `null`;
* `updatedAt` is refreshed;
* audit event `TICKET_REOPENED` is created.

Success:

```http
200 OK
```

### 5.5 Close

```http
POST /api/v1/tickets/{ticketId}/close
```

**Access:** `ADMIN`

Preconditions:

* status = `RESOLVED`;
* requester has confirmed the resolution.

Result:

```text
RESOLVED -> CLOSED
```

`CLOSED` is final in MVP.

Creates `TICKET_CLOSED` audit data.

Success:

```http
200 OK
```

## 10. Audit history

```http
GET /api/v1/tickets/{ticketId}/audit
```

**Access:** `ADMIN` in MVP.

Response order:

```text

```

Example:

```json
[
  {
    "id": "uuid",
    "action": "TICKET_ASSIGNED",
    "actor": {
      "id": "uuid",
      "name": "Admin Root",

  }

```

* `TICKET_CREATED`
* `TICKET_ASSIGNED`

* `TICKET_UNASSIGNED`

* `TICKET_CLOSED`
* `COMMENT_ADDED`
* `CATEGORY_CHANGED`

`STATUS_CHANGED` uses `details` to record the previous and new status.

## 11. Error response contract

All API errors use one consistent structure:

```json
{
  "timestamp": "2026-09-03T10:20:00Z",
  "status": 403,
  "error": "FORBIDDEN",
  "message": "You are not allowed to access this ticket.",
  "path": "/api/v1/tickets/27"
}
```

Validation errors may additionally contain `fieldErrors`:

```json
{
  "timestamp": "2026-09-03T10:20:00Z",
  "status": 400,
  "error": "VALIDATION_ERROR",
  "message": "Request contains invalid fields.",
  "path": "/api/v1/tickets",
  "fieldErrors": {
    "title": "Title is required.",
    "categoryId": "Category is required."
  }
}
```

### Standard status codes

* `200 OK` — successful retrieval/update/action.
* `201 Created` — resource created.
* `204 No Content` — successful operation with no response body.
* `400 Bad Request` — malformed or invalid request.
* `401 Unauthorized` — missing or invalid authentication.
* `403 Forbidden` — authenticated but not permitted.
* `404 Not Found` — resource does not exist, or is deliberately hidden by authorization policy.
* `409 Conflict` — duplicate or conflicting state.

Controllers should not invent endpoint-specific error formats.

## 12. API security requirements

1. All protected endpoints require a valid JWT.
2. Role checks are enforced by the backend.
3. Resource ownership and assignment checks are enforced by the backend.
4. The server derives requester, author, confirmer, and actor identities from the authentication context.
5. Clients cannot self-select elevated roles during self-registration.
6. Clients cannot submit trusted audit entries.
7. Deactivated users cannot authenticate.
8. Authorization failures must not expose data from tickets the caller is not allowed to see.

## 13. Frontend integration notes

The current Bolt frontend uses mock services and will eventually call this REST API.

The frontend may reshape API data for display, but backend data remains authoritative.

The following mock-only concepts should be removed or adapted during API integration:

* duplicated `Agent` entity;
* duplicated requester/agent names stored as ticket persistence fields;
* nested comments as persistent ticket data;
* client-generated ticket numbers;
* mock JWTs;
* client-controlled requester identity.

The frontend should retain UI-specific state only where it does not conflict with backend-authoritative state.

## 14. Explicit non-MVP scope

The following are intentionally excluded from v1:

* automatic ticket assignment;
* agent availability management;
* reopening closed tickets;
* automatic ticket closure after a timeout;
* physical deletion of users/categories with historical records;
* real-time WebSocket updates;
* attachments;
* advanced full-text ticket search;
* SLA/escalation engine;
* email/push notification workflows beyond the minimal event hooks required by the core workflow.

These can be added later without replacing the core ticket/domain model.
